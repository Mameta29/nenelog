## スパイク1: iOS — SFSpeechRecognizer/SpeechTranscriber 日本語オンデバイス+背景audio連続認識

- 判定基準: ja_JP で `supportsOnDeviceRecognition == true`、Background Modes: audio 下で画面オフでも連続認識が継続、speak→300ms再開ループが安定
- 結果: **合格(2026-08-31、iPhone XS / iOS 18.7.10)**。
  `SFSpeechRecognizer` は63ロケールを返し、`ja-JP` は `available=true`、
  `supportsOnDeviceRecognition=true`。画面オンで「右スタート」「左スタート」を認識し、
  TTS読み上げ後300msで認識を再開して2発話を連続処理できた。
- 初回は連続音声ストリームが短い発話を `isFinal` にせず、TTSへ進まなかった。
  partial更新後800msの無音を発話終端として確定する処理を追加し、修正後に
  `partial → FINAL(silence) → speak done → recognition start` のループを確認した。
- 短時間の画面オフ試験では「右スタート」の認識・TTSまでは成功したが、TTS後に
  録音I/Oを再起動すると `AVAudioSessionErrorCodeCannotStartRecording` (`!rec` / 561145187)
  が連続した。バックグラウンドでは停止済み録音I/Oを新規開始できないため、音声I/Oと
  input tapは維持し、TTS中だけ認識requestを外して音声バッファを破棄する方式へ修正。
  修正版では画面オフのまま「右スタート」「左スタート」の2発話を連続認識し、
  両方のTTS読み上げに成功。`!rec`は再発しなかった。
- **デバッガなしの画面オフ状態で5分継続して合格**。約10秒・2分30秒・4分30秒時点の
  3コマンドをすべてオンデバイス認識してTTS応答し、各応答後も認識を再開。
  クラッシュ・`!rec`再発なし。
- iOS 18では `SpeechTranscriber` が利用できないため、R11の方針どおり
  `SFSpeechRecognizer` を主経路にする。`SpeechTranscriber` はP2の将来最適化とする。
- リスク連動: R3

| 確認項目 | 結果 |
|---|---|
| supportedLocales に ja 系 | ✅ 63ロケール、`ja-JP` あり |
| ja-JP onDevice | ✅ `available=true` / `onDevice=true` |
| 画面オフでの連続認識継続 | ✅ デバッガなしで5分、3コマンド認識+TTS、`!rec`再発なし |

| iOS 26 SpeechTranscriber の有無・ja対応 | ➖ iOS 18実機では対象外。SFSpeechRecognizer経路を採用 |

## スパイク2: Android(Pixel実機)— オフライン日本語+FGS×画面オフ×連続認識

- 判定基準: `isOnDeviceRecognitionAvailable == true` かつ機内モードで ja-JP 認識が動く。FGS 開始→画面オフ→5分以上、認識ループが途切れない(restartsは正常)
- 手順: Speech Spike 画面 →「能力ログ確認」→「画面オンで開始」で認識確認 → 機内モードで再確認 → 「FGSで開始→画面オフ」→ 5分後に画面オンでログ確認
- 結果: **合格(2026-08-31、Pixel 8 / Android 17)**。`ja-JP` の
  `createOnDeviceSpeechRecognizer` で「右スタート」「左スタート」「左ストップ」等を認識し、
  TTS 読み上げ後の認識再開を連続確認。画面オン経路の成立を確認した。
- 初回は TTS 後の再開で `ERROR_SERVER_DISCONNECTED(11)` が自己増殖した。
  原因は再開時の `cancel()` が追加の `onError` を発生させる実装だったこと。
  再開予約の単一化・`cancel()` 除去・切断時の recognizer 再生成を行い、修正後は
  複数コマンドを連続認識+読み上げ。大量エラーは再発せず、無音時の `NO_MATCH(7)` のみ。
- 端末は `onDeviceRecognitionAvailable=true`、`recognitionAvailable=true` を返した。
  ただし `CONFIDENCE_SCORES` は認識成功時も `0.0` のため、P0 の判定には使用しない。
- **FGS×画面オフは5分08秒継続して合格**。画面オフ中に「右スタート」
  「左スタート」「ストップ」を認識してTTS応答し、無音タイムアウトを含む31回の再開後も
  クラッシュ・`SERVER_DISCONNECTED`再発なし。「ストップ」は2回目で認識したため、
  生活環境でのコマンド成功率計測・同義語調整はR7として継続する。
- **機内モード(Wi-Fi・モバイル通信ともにオフ)でも合格**。
  `createOnDeviceSpeechRecognizer` で「右スタート」を認識し、TTS応答と認識再開に成功。
  直前の1回は「ミニスタート」と誤認識したため、オフライン可否は解決済みとしつつ、
  認識成功率はR7で計測・改善する。
- リスク連動: R2(不可なら オンライン認識フォールバック+文言調整、docs/03)

| 確認項目 | 結果 |
|---|---|
| isOnDeviceRecognitionAvailable | ✅ `true`(Pixel 8 / Android 17) |
| 機内モードで ja-JP 認識 | ✅ Wi-Fi・モバイル通信オフで「右スタート」認識+TTS成功 |
| FGS×画面オフで連続認識(5分) | ✅ 5分08秒継続。画面オフ中に3コマンド認識+TTS成功 |
| TTS読み上げ→認識再開ループ | ✅ 複数回連続成功 |
| 再起動ループの onError パターン | ✅ `NO_MATCH(7)`は正常再開。`SERVER_DISCONNECTED(11)`暴走を修正済み |

## P0授乳縦切り本実装(2026-09-01)

- タップ、iOS Siri App Intents、iOS/Android L2音声がすべて同じ
  `NursingSessionService` + SQLDelight DBを使う構成に統合。ActiveSessionは操作ごとに
  永続化し、停止時は完了Event追記+ActiveSession削除を1transactionで確定する。
- 同じ側の重複開始はタイマーをリセットしない。左右切替、プロセス再作成後の復元、
  停止中の停止、90分自動保存、undo(打ち消しEvent)をJVM統合テスで確認。
- Composeの最小ホームを日英リソース・システムダークモード・48pt以上の操作面・
  色だけに依存しない状態文言で実装。左右タイマー、停止保存、最近の授乳を表示。
- Android通常ホームの授乳開始からマイクFGSを自動開始。画面オフ中も「左」「右」
  「ストップ」にTTS応答し、ストップ読み上げ完了後にFGSを終了。常駐通知の
  「停止して記録」でも確定できる。技術スパイクの2重ランチャー表示は解消。
- iOS通常ホームの授乳開始/停止を、実機合格済みのSFSpeechRecognizer+
  AVSpeechSynthesizerループに接続。認識結果は固定文法で解釈しDBへ保存、未定義発話は
  読み上げず無視する。
- 自動検証: `:shared:domain:jvmTest`、`:shared:data:jvmTest`、Android debug APK、
  iOS arm64実機向けXcode buildは成功。**G2の実授乳完走は端末再接続後に実施する。**
- Pixel 8の本番ホームから、英語のLeft/Right/Stop、日本語の左/右/ストップ、
  日本語の画面オフFGS、機内モード+Wi-Fiオフの完全オフラインを順に完走。
  Stop後のサマリー読み上げ、Event保存、FGS終了まで確認した。Androidが端末言語
  `en-JP-u-mu-celsius`を返して`LANGUAGE_NOT_SUPPORTED(12)`になったため、アプリが
  対応する`en-US`/`ja-JP`へ正規化し、Android標準のアプリ別言語設定も追加した。
- 一方で実発話はコマンドによって2〜3回の言い直しがあり、終了サマリーの漢字「右」を
  TTSが「う」と誤読した。方式の成立は確認できたが製品精度の合格ではない。台本を
  「みぎ、N分。ひだり、N分」へ変更し、Android API 33+の固定語バイアス、最大5候補からの
  完全文法一致を実装。改善版のPixel 8実機確認では、終了サマリーが「みぎ」「ひだり」と
  正しく読み上げられ、TTS誤読は解消した。一方、短い通常発話試行は5発話中3成功
  (「右スタート」→「ミニスタート」1回、`NO_MATCH` 1回)に留まった。これは正式な成功率
  測定ではないが目標90%には明確に未達のため、再実機計測後までG2とR7は未完扱いとする。
- 認識サイクルID、`onReadyForSpeech`、`onBeginningOfSpeech`を追加計測したところ、Pixelの
  オンデバイス認識は静音時にも`onBeginningOfSpeech`を通知するため、同コールバックを実発話の
  証拠には使えないと判明。一方、1語の「右」は正しい途中候補`右`の直後に最終結果なしの
  `NO_MATCH`となる場合と、最終結果`三重`になる場合を実測した。前者に対し、最後の途中候補が
  固定文法へ完全一致した場合だけ採用するフォールバックと共通domainテストを追加した。
- 更新版の静音・通常声による短期比較では、「右」0/1(`三重`)に対し、推奨形の
  「右スタート」「左スタート」「ストップ」は各1回目で成功し3/3。終了サマリー、DB保存、
  FGS終了まで完走した。長い形式をAndroidの暫定推奨発話とするが、標本が小さいため正式な
  90%判定には使わず、コマンド別反復測定を継続する。
- その後、診断画面でプロンプト表示後に1回だけ発話し、言い直しを認めない静音・通常声の
  30発話試験をPixel 8で実施した。リセット前の練習1回は除外し、10セット×3コマンドを採点。

  `左アート`、`左サド`、`左里`、`やりさと`、`いきなりスタート`、`左下と`などに分散した。
